# Windows

The native Windows platform, `src/claude_launcher/platforms/windows/`, and what was learned building it; WSL is at the end. Imported into CLAUDE.md.

## Layout

| Path | Role |
|---|---|
| `bin/claude-session-hook.py` | The session hook: the bash hook's record, in Python. It reads Claude's JSON as UTF-8 bytes (`-I` ignores `PYTHONIOENCODING`, and a pipe would otherwise be read in the ANSI code page), writes nothing without `CLAUDE_PID` (its parent is cmd, not Claude), and retries a write or removal for a moment if another process has the file open. The boot ID is the boot counter as 32 hex digits. |
| `platforms/windows/__init__.py` | Windows' `Platform`: fzf picks `cmd` itself (`SHELL=cmd`), the core's command line quoted for it (`cmd_quote`), fzf on a localhost port, files in `%LOCALAPPDATA%\claude-launcher` (`local_app_data`). The host is imported only in `platform()`, so WSL, which uses `eventlog` and `terminal`, never loads ctypes. |
| `platforms/windows/setup.py` | What the installer adds, in the data directory: `claude-session-hook.cmd` and `claude-launcher.cmd`, which find Python each time they run (`_RUN`), and beside each an entry script (`entry_script`) that checks for Python 3.10+ and runs the repo's script. Also `claude-launcher.cmd` in `%USERPROFILE%\.local\bin` (where Claude Code's installer puts `claude.exe`), which hands over to the data directory's (`_SHIM`), and the "Claude Code" Windows Terminal profile. |
| `platforms/windows/terminal.py` | The profile as a fragment (`%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\claude-launcher\`), with the Claude Dark scheme built from `themes/claude-dark`. Uninstalling deletes the fragment; Windows Terminal's own settings.json is never edited. The profile's GUID never changes: Windows Terminal keeps the user's changes to it under that. Shared with WSL. |
| `platforms/windows/eventlog.py` | Restarts and logoffs from the System log through `wevtutil.exe` (any user can read it; the Security log needs an administrator). Shared with WSL. |
| `platforms/windows/host.py` | The boot counter (registry `BootId`), processes (`NtQueryInformationProcess` for command lines, `GetProcessTimes` for when they started), `msvcrt` locks, the console (`CONOUT$`, `CONIN$` with VT input; the old console mode is put back at exit). ctypes with declared argument types, on its own `WinDLL`s. |
| `install.ps1` | Finds Python 3.10+ the way the .cmd files do, offers to install it with winget if there's none, then runs `install.py` and shows its lines. ASCII only (a test checks): Windows PowerShell 5.1 reads a script without a BOM in the code page. `$ErrorActionPreference` stays `Continue`: `Stop` makes a native program's stderr fatal in 5.1. It puts the console's output encoding back when it's done. CI lints it with PSScriptAnalyzer and runs it, then `-Uninstall`, in 5.1. |

## Rules

- **The .cmd files are ASCII and hold no paths.** cmd reads a batch file in the console's code page, so a path with "é" in it comes out wrong. They run the entry script beside them (`%~dp0`); the entry scripts hold the repo's path, ASCII-escaped. Every .cmd starts with `setlocal DisableDelayedExpansion`, which may be on by default (the registry) and would eat a "!" in a path.
- **No user text on a command line cmd parses.** Claude quotes an argument only when it has a space, tab or quote, so `C:\Users\A&B\...` would reach cmd unquoted and be split at the `&`. settings.json runs `<SystemRoot>\System32\cmd.exe /d /v:on /c !LOCALAPPDATA!\claude-launcher\claude-session-hook.cmd start`: delayed expansion puts the path in after cmd has parsed the line, the value isn't parsed again, and a command that starts with a drive isn't split at its spaces. The profile names its .cmd by `%LOCALAPPDATA%`, which Windows Terminal expands. Checked in the VM from user directories with spaces, brackets, `&`, `^`, `%`, `!` and non-ASCII names (`tests/windows/test_hook_live.py`).
- **System32's cmd.exe, never `%ComSpec%`**, which can be another shell (TCC) that reads `/d` and `/c` its own way.
- **Python is found each time it's needed**: the first `python.exe` on PATH, unless it's in WindowsApps (the Microsoft Store's stand-in, which only offers to install Python, or a Store or install-manager Python's alias), then `py -3`, then that WindowsApps `python.exe` after all. A Python older than 3.10 makes the entry script exit 9310, and the .cmd tries the next one; the last says "claude-launcher needs Python 3.10 or newer". So a new, moved or replaced Python just works. The hook takes about 57 ms in the VM (36 for a fixed `python.exe`; PowerShell would be 530 ms; Git is optional for Claude on Windows, so no Git Bash).
- **Running claude**: found on PATH; npm's `claude.cmd` (CreateProcess doesn't try PATHEXT) runs through System32's cmd with each argument quoted for a batch file (`launcher._batch_arg`: `"` doubled, `%` as `%%cd:~,%`, no line breaks).
- **fzf and cmd.** With `--with-shell`, fzf treats the shell as unknown and quotes `{q}` POSIX-style ('a'), and it doesn't wrap the command for `cmd /s`. Without it, fzf takes `$SHELL` (OpenSSH and Git Bash set it to PowerShell or bash), else `cmd`; for `cmd` it runs `cmd /s/c "COMMAND"` and quotes placeholders the way programs split their command lines, with `^` before `cmd`'s special characters. So the launcher runs fzf with `SHELL=cmd` and no `--with-shell`, and `cmd_quote` quotes the core's arguments the same way. The program itself is in plain quotes: `cmd` finds it by them, and `^"` isn't one. `tests/windows/test_cmd_live.py` round-trips hostile arguments through cmd.
- **No Unix sockets in Windows' Python**, so fzf listens on `localhost:0` and gives its commands the port in `FZF_PORT`. Every request carries the run's `FZF_API_KEY`.
- **No fork**: a first press's second half runs as a detached core process (`ui restore-header`).
- **Text is UTF-8 with `\n`, everywhere.** Windows' Python writes the code page (cp1252, no ↻) and `\r\n` by default, to files and to pipes; fzf would show the `\r`, and `subprocess` with `text=True` hung on a ↻ in fzf's input. Give every text read and write `encoding="utf-8"` (and `newline=""` for writes), or pass bytes to a subprocess; the core and launcher reconfigure stdout and stderr (`text.utf8_out`).
- **fzf leaves the console's last column unused** (writing it wraps the line), so the picker lays out one column narrower (`columns_lost`).
- **`TERM` is unset in Windows' consoles**, which take escapes anyway, so only `TERM=dumb` turns off colors and the title there (`title.dumb`). Windows Terminal (1.18 and later at least) answers the color queries and device attributes; the picker asks and switches as anywhere else.
- **conhost** (the old console window) runs the picker, the title and Ctrl-C as Windows Terminal does, but doesn't answer the color queries, so its colors are left alone; Consolas has no ↻.
- **Ctrl-C through `claude-launcher.cmd`**: fzf and Claude read the console raw, so Ctrl-C is a key to them and `cmd` never asks "Terminate batch job (Y/N)?" (checked: quitting the picker, and quitting Claude with two presses).
- **winget** installs Python from a desktop session only; over SSH it fails. `install.ps1`'s offer was checked with Python hidden: it installs Python 3.13 for the user and carries on.
- **`HOME` isn't home**: Git Bash sets it to `/c/Users/...`. Home is `USERPROFILE`. Environment names are matched without case (`SystemRoot`, `SYSTEMROOT`).
- **Paths**: see `pathtext.PathText("nt")`; any drive letter, and shares (`\\srv\share` with or without the trailing `\`). Claude names a log directory after the path with every non-alphanumeric character as `-` (`C:\Users\me` is `C--Users-me`), as on Linux.
- **A pid is only the record's Claude if that process started by the record's start** (`claude_running(pid, started)`, from `GetProcessTimes`, with 10 s to spare): Windows reuses pids quickly.
- **Restart and logoff detection** (`eventlog.py`). Restart or power off: the boot's last User32 1074 ("initiated the restart") to Kernel-General 13 ("shutting down"); without a 13 (a crash, a power cut), the boot's last logged event. A 1074 more than 10 minutes before the boot's end (`_BEGUN_MAX`: a shutdown scheduled for later, or called off) isn't the one, and a restart spans at most 2 minutes (`_SPAN_MAX`). Logoff: Winlogon 7002 with this user's SID (`whoami.exe /user`, asked once); Windows logs one at a restart too, and the restart wins. A boot runs from one Kernel-General 12 to the next; filter by provider as well as ID, since Wininit logs 12 and 13 too. Sort by time, not by the log's order: a clock that was set wrong and then right leaves "later" events earlier in the log. The log is read once per picker run, from the earliest record's start (at most 8 days back), and filtered per record. Measured in the VM: 1074 → 7002 (+0.8 s) → 13 (+4 s) → 12 at the next boot. Windows Update restarts on its own (TrustedInstaller, "Upgrade (Planned)"), with the same events. `tests/test_windows_eventlog.py`'s fake wevtutil evaluates the XPath it's given, so a wrong query fails a test.
- **Fast Startup.** The boot counter (`BootId`) goes up on every full boot. A Fast Startup shutdown (measured in the VM) logs 1074 ("power off", by Explorer) and this user's 7002, then hibernates: Kernel-Power 42, and 107 at power on, with no Kernel-General 13 or 12, Kernel-Boot 27 "boot type 0x1", and `BootId` unchanged. So the record's boot is still the current one. `_fast_startups` finds it as a 1074 followed by a 42 within `_FAST_STARTUP_GAP`, with no 13 between, and it counts as a restart from the 1074 to the 42 (hibernating on its own logs no 1074); its 7002 is a logoff, which the restart wins over. `shutdown /s /hybrid` from an SSH session shuts down fully instead; and with Credential Guard on (the VM's default), hibernating in the VM fails and reboots (Kernel-Power 41), which the picker treats as a crash.
- **What Claude gives a hook on Windows** (2.1.312): the same stdin as on Linux (`/exit` is `prompt_input_exit`, closing the terminal `other`), `CLAUDE_CODE_ENTRYPOINT=cli` (`sdk-cli` for `claude -p`), `CLAUDE_PID`. A shell-form hook runs as `bash -c "bash COMMAND"` under Git Bash, or PowerShell without it. `bash` on PATH is `System32\bash.exe`, WSL's.

## WSL

`platforms/wsl/` is Linux (its host, the bash hook, the `~/.local/bin` links) with these differences. It's picked when the kernel's release says "microsoft" and a WSL marker is there (`WSL_DISTRO_NAME`, `/run/WSL`, or `binfmt_misc/WSLInterop`), so Docker Desktop's containers, which run the same kernel, stay Linux.

- **The boot is the distro's.** Every distro shares one VM, and so its boot ID and uptime, and `wsl --terminate` stops one distro while the VM runs on. Under WSL's kernel, the hook and `LinuxHost` make the boot ID from the VM's (its first 20 hex digits) and pid 1's start (12 more), and `boot_start` is that start.
- **Restarts and logoffs** (`events.py`): Windows' own, from `eventlog.py` through interop, since a distro's boot ends with Windows'. WSL or the distro stopping by itself (`wsl --shutdown`, `--terminate`, `--update`) is WSL's own reason, `wsl-stop` ("open when WSL stopped"; WSL's `Platform.reasons`, ranked after restart and logout), at the distro's start. It kills Claude, so the record has no end, and a record without one is closed by the first event after it started; a tab closed earlier has its own end and isn't counted. A Windows restart or logoff stops WSL too, and wins over it. Without interop, only that last one is known.
- **Windows' programs** (`interop.py`) run by their full path in System32, found on PATH or on whichever Windows drive is mounted (`/proc/mounts`): `appendWindowsPath=false` takes them off PATH, and `[automount] root` moves the drives.
- **Setup** (`setup.py`): first it finds the distro (`WSL_DISTRO_NAME`, else `wslpath -w /`, since sudo clears the environment). Then a "Claude Code (<distro>)" Windows Terminal profile, written through the mounted drive (`%LOCALAPPDATA%` from `cmd.exe /d /u`, whose output is UTF-16, so a non-ASCII user name survives), with its own GUID per distro, beside native Windows' profile. It runs `wsl.exe -d <distro> -u <user> --cd ~ -- bash -lc "~/.local/bin/claude-launcher || exec bash"`, starting in `wslpath -w ~`. `--icon` takes a .png, kept in the data directory. Without interop the profile is skipped with a warning and the install still succeeds: the launcher runs in any terminal.

Checked in the VM (WSL 3.0.3, Ubuntu 26.04 with systemd): install.sh, the profile in Windows Terminal, a Claude session, `wsl --shutdown`, and the session offered back; `wsl --terminate` keeps the VM's boot ID (hence the distro's own).

## Testing

The suite runs on Windows (`python -m pytest --basetemp=C:\t`; a short temp directory keeps deep test paths under 260 characters), in CI on `windows-latest` with Python 3.10 and 3.14, and in WSL (not in CI: GitHub's runners can't run WSL 2), where a Linux desktop's own tests (`desktop_only`, such as install.sh's, which would write to the real Windows Terminal) are skipped; the WSL installer's tests fake interop and run anywhere. `tests/windows/` (live: the hook and launcher from hostile user directories, cmd quoting, the .cmd's Python search, the event log) runs only on Windows. Tests that drive a pseudo-terminal (`test_e2e.py`, `test_theme.py`) are POSIX-only; on Windows the launcher is driven over SSH, whose sessions are real consoles (ConPTY), and its screen rendered with pyte.

A Windows 11 VM (QEMU, no root needed) was used for all of the above: an unattended install, SSH for commands, QMP for screenshots and keys on its desktop (Windows Terminal), and WSL inside it. Its clock must be local time (`-rtc base=localtime`), or restarts log events hours apart.
